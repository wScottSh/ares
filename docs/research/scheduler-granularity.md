# Scheduler granularity and its host cost (#9)

Map [#1](https://github.com/wScottSh/ares/issues/1), issue [#9](https://github.com/wScottSh/ares/issues/9). ADR 0001 (`origin/feat/design:docs/adr/0001-timing-core.md`) already decided the shape: a conservative discrete-event timeline with the CPU as the outer loop, a per-instruction `horizon()` check, CPU and RSP alternating per instruction while the RSP runs, and one RI arbiter that grants timestamped bursts. This document measures what that shape costs on the host, so the ADR's run-budget table can use measured rows instead of guesses.

## Answer

- Today's interpreter already runs at the finest granularity the ADR needs. `CPU::main` calls `synchronize()` after every instruction, and that call runs every device's `main()` and the event queue. 96% of the syncs cover 2 CPU clocks or fewer (measured).
- The boot-to-600-fields workload understates the cost. On the MM bench's South Clock Town window (`sct`), the RSP runs during 53% of CPU instructions. During boot it runs during 7%. Today's interpreter needs about 14 s for the `sct` window, against the 8.5 s that ADR 0001 cites for boot (measured).
- A per-instruction horizon check is too cheap to measure. Skipping the full sync while no device is due saves 2.9 to 3.8 ns per skipped sync (measured).
- CPU-RSP alternation is the expensive part. With only the RSP stepped per CPU instruction, it costs about 8.3 ns per CPU instruction while the RSP runs, or about 2.1 s per 600 `sct` fields. ADR 0001 assumed 3 ns and 1.2 s (measured against assumed).
- An arbiter-shaped loop costs 20 to 30 ns per granted burst on a quiet host, and up to 55 ns under load. That covers the argmin pick, bank state, the byte copy and the client callback. At an estimated 17 to 32 M bursts per 600 `sct` fields, that is 0.3 to 1.8 s. ADR 0001 assumed 50 to 100 ns and 1 to 2 s (measured cost per burst, inferred burst count).
- The scheduling shape the ADR chose, measured with today's devices, takes about 11.8 s for the `sct` window. That leaves about 106 s of the 120 s budget for the CPU pipeline model, the RDP pixel engine and the rest (inferred from the measured rows).

## Setup

- Host: this machine (Windows 11, 12 logical CPUs, TSC at 3.89 GHz). Build: `tools/n64-timing/build.sh` (MSYS2 clang64, RelWithDebInfo, `-O2 -march=native`, ThinLTO).
- Worktree `C:\Users\Scott\repos\ares-wt\measure-9` on `origin/feat/harness` (`c8592d16a`), plus `tools/n64-run` and `tools/n64-timing/mmbench` from `origin/feat/mmbench` (`a1f3544ab`) so the runner can play the bench's input scripts.
- Instrumentation is measurement-only and is not delivered as code. `scheduler-granularity/instrumentation.patch` holds the core changes and `scheduler-granularity/n64-run-on-mmbench.patch` holds the runner changes. They add counters and these switches, all read from the environment at startup:
  - `M9_MODE=0` is today's behavior: a full `synchronize()` after every instruction.
  - `M9_MODE=1` is the horizon skip. The CPU calls `synchronize()` only while the RSP runs or once its clock passes a horizon. The horizon is the earliest of: the next VI, AI, RDP or PIF step, the halted RSP's next 128-clock step, the next queue event (PI, SI, DMA completions), and the next COMPARE match. `CPU::queueInsert` lowers it.
  - `M9_MODE=3` is the ADR shape. While the RSP runs, the CPU steps only the RSP after each instruction (`rsp.main()` with the RSP's clock debt). Everything else waits for the horizon, as in mode 1.
  - `M9_MODE=2 M9_BATCH=N` syncs everything once the CPU is N clocks ahead. This is a floor, not a correct schedule.
- Workloads:
  - `boot`: cold boot to 600 VI fields, `--rdp none`. Script `scheduler-granularity/matrix3.sh`, configs `configs3.txt`, runner `bench.sh`.
  - `sct`: the mmbench `sct` scene script (`sct-script.txt`, generated by `mmbench.py` on `origin/feat/mmbench`). Cold boot through map select to South Clock Town, then a 600-field window of stick input starting at field 329. Only the window is counted: the runner snapshots counters, TSC and thread CPU time at the script's `mark window` step. Scripts `matrix4.sh`, `matrix5.sh`, `bench-sct.sh`.
- Noise: other agents were building and running emulators on this host during the runs. Single runs varied by up to 2x. Each configuration was interleaved with the others and repeated 6 to 10 times. The tables report the minimum, which is the least disturbed run, and the median. `analyze.py LOG PREFIX [window]` produces each table from the logs.
- `base` is the uninstrumented harness runner. The counters cost about 9% on boot: `base` minimum 8.51 s against `M9_MODE=0` minimum 9.28 s (measured).

### Horizon check per instruction

Every mode above already pays one compare and branch per instruction (`Thread::clock >= horizon` or `>= batch`), so the check alone was not isolated. Between batch 512 and batch 4096 on boot, 3.3 M fewer syncs move the minimum by 0.19 s, which is inside run-to-run noise. The check itself is a load, a compare and a predictable branch. Its cost is below what this host can resolve at 600 fields: under 0.3 s for 689 M instructions (inferred bound). The ADR's "+5 ns" row is dominated by the pipeline scoreboard, which this unit did not measure.

### Is the horizon skip exact today?

No, and it should not be expected to be. Every run of every mode marks the window at field 329, and modes 0, 1 and 3 show the same VI origin (`0x7daa80`) at field 928. The cumulative counters at field 928 differ, though: `cpu_cycles` is 1,502,344,013 (mode 0), 1,502,343,980 (mode 1) and 1,502,343,935 (mode 3), and `rsp_busy_clocks` is 905,367,450, 908,126,169 and 905,454,336 (measured, last row of `stats-x5-*-r1.tsv`). Today a CPU read of an RCP register does not catch the device up first, so skipping syncs changes what the CPU sees. ADR 0001 handles this by calling `catchUp` before every cross-device access, and checks it with `--step-cap`. The cost numbers above still hold, because the instruction counts in every mode agree within 0.3%.

### Arbiter-shaped loop

`scheduler-granularity/arb2.cpp` is shaped on ADR Decision 2. Twelve requesters post bursts into per-requester FIFOs. Each timeline step scans six actors for the minimum. Each bus decision picks `argmin(rank, arrival)` over the arrived FIFO heads, charges wire time from an 8-bank open-row and dirty-bit model, copies 8 to 128 bytes between an 8 MiB array and the client's buffer, and calls the client's `granted()` through a function pointer. The client then posts its next burst. Burst sizes and the mix follow the `sct` counts below. A contention factor scales the clients' think time. Command:

```
clang++ -O2 -march=native -std=c++17 arb2.cpp -o arb2.exe && ./arb2.exe 30000000
```

Results, 5 reps of 30 M grants each (`scheduler-granularity/arb2-results.txt`), measured:

| Contention | Mean wait per grant (units) | ns per grant, min of 5 | ns per grant, max of 5 |
|---|---|---|---|
| 0.25 (bus mostly idle) | 6.7 | 23.8 | 42.9 |
| 1.0 | 41.6 | 19.7 | 40.1 |
| 4.0 (requesters always queued) | 360.6 | 27.7 | 53.4 |

The loop does not include the device-side work of building a burst or the `catchUp` that the grant triggers in a stepped client. Those belong to the device rows of the budget.

## Budget against 2 minutes for 600 fields

Rows for the `sct` window. "Today" rows are measured on this host. ADR rows are the ADR's own estimates, kept for comparison.

| Part | Host time | Basis |
|---|---|---|
| Interpreters today, full sync every instruction | 14.05 s instrumented, about 12.9 s without counters | measured; uninstrumented value inferred from the 9% boot overhead |
| Same, with the ADR scheduling shape (horizon skip, CPU-RSP alternation only) | 11.81 s | measured, mode 3 |
| RI arbitration | 0.3 to 1.8 s | measured cost per burst times inferred burst count |
| CPU pipeline scoreboard | not measured | ADR estimate 3 s |
| RDP pixels, spans, commands | not measured | ADR estimate 4 to 10 s |
| VI compose, AI, PI, SI | not measured | ADR estimate under 1 s |
| Total so far | about 13.6 s measured and bounded, about 22 to 28 s with the ADR's unmeasured rows | inferred |
| Remaining against 120 s | about 92 to 98 s | inferred |

Changes this suggests for the ADR budget table:

- Anchor the "interpreters today" row on the `sct` window (about 13 to 14 s), not on boot (8.5 s). Boot leaves the RSP halted 93% of the time.
- Replace "catchUp alternation, 400 M calls at 3 ns, 1.2 s" with "249 M CPU instructions while the RSP runs, 8.3 to 8.6 ns, 2.1 s". Most of that is entering and leaving `RSP::main` for one RSP instruction. Stepping the other devices on the same boundary as well costs another 7 ns per instruction, so `catchUp` must not walk idle actors.
- Replace "RI decisions 50 to 100 ns" with "20 to 55 ns measured in an arbiter-shaped loop". Count the RDP bursts once the RDP actor exists.

## What granularity is needed

- CPU and RSP: one instruction each, alternating while both run. This is the ADR's choice and today's behavior. Batching the RSP would save about 2 s per 600 `sct` fields, but the ADR rules it out because DMEM and `SP_DMA_BUSY` reads must see the DMA state at the exact clock.
- Other devices and DMA engines: only at their own events and at the arbiter's decision times. Stepping them on every CPU instruction is today's largest avoidable cost: 2.9 to 3.8 ns per instruction while the RSP is halted, plus about 7 ns per instruction while it runs.
- Bus contention: one decision per burst at rclk edges, as the ADR specifies. Per-transaction arbitration is affordable at 20 to 55 ns per burst.

## Open questions

- The CPU pipeline scoreboard cost per instruction (ADR row "+5 ns") was not measured here. It needs the scoreboard code from plan T5 or later.
- RDP burst counts need the RDP actor. The 5 to 20 M range is an estimate.
- The `sct` minimums come from a shared, noisy host. A rerun on an idle machine should tighten the medians toward the minimums.
- The RSP-only alternation still pays for entering `RSP::main`, the `dmaStep` call and the RSP pipeline setup for each RSP instruction. A dedicated single-step entry point may cut part of the 8.3 ns. This was not tried.
