# VR4300 dirty miss and write buffer protocol

Ticket: wScottSh/ares#26. Map: wScottSh/ares#1. Builds on #6 (`docs/research/cpu-memory-costs.md` on branch `research/cpu-memory-costs`) and the nemu64 failure triage (`docs/research/nemu64-timing-failures.md` on `research/nemu64-timing-failures`). Research date: 2026-10-04.

Target: NTSC retail NUS-001 with Expansion Pak.

Units:

- **CPU cycle** = PClock, 93.75 MHz.
- **RCP cycle** = MasterClock = SClock, 62.5 MHz. 1 RCP cycle = 1.5 CPU cycles.
- ares counts half-CPU-cycles (`step(N * 2)`). Every ares number below is converted to CPU cycles.

Snapshots: this fork `59158c28a`; N64_MiSTer `5725381`; cen64 `e0641c8`; nemu64-test `9a8b9f7`; n64-systemtest `196f542`; rasky/n64-systembench `845635c`; N64-IPL decomp (scratch copy); NEC VR4300 User's Manual U10504EJ7V0UM00 (7th ed.); MIPS "R4300 Data Sheet, Rev 0.3, April 1997".

Inferences are marked **[inference]**. Everything else is quoted or read from the cited source.

## TL;DR

- **Dirty D-miss order: fill first, writeback after.** Three primary documents say so in so many words:
  - NEC §12.5.2/§12.5.3 (p.304): "The above read operation must be completed before the data in the dirty state is written."
  - NEC §4.9 (p.120) and §11.3.2 (p.280-281).
  - R4300i datasheet p.8-9: "the dirty data is then stored in the flush buffer until the requested data is returned".
  
  The victim line goes into the write buffer as **one 4-word block write occupying 2 of the 4 entries** (datasheet p.9; SysCmd block write size "4 words (for D-cache only)", NEC Table 12-8). The pipeline restarts after the fill. The writeback then drains while code runs.
  
  MiSTer does the opposite: writeback first, then fill, in one FIFO (`cpu_datacache.vhd:376-383, 488-523`). No test constrains that, and it contradicts the manual. **Judged: fill first.**
- **What each phase costs:**
  - Fill: the clean-fill numbers apply. That is **40 stall / 41 total** (hardware, nemu64-test).
  - Writeback bus occupancy: **about 27-31 CPU cycles (18-21 RCP)**. This is derived from a hardware memset benchmark on n64brew (MI page): 1 MiB of 64-bit cached writes takes 49.8 ms, which is 71.2 CPU cycles per 16-byte line **[inference: the loop shape is not published]**.
  - An isolated dirty miss should stall about as long as a clean one (about 40). The writeback only delays the *next* SysAD transaction **[inference]**.
  - ares charges 40 + 40 = 80, serially (`cpu/dcache.cpp:7,16,54-58,83-87`).
- **I-cache fill:** one 8-word sequential block read. The pipeline restarts only after the whole line (NEC §11.3.3, §12.12.2). That is about **43-47 stall** (from #6). The I-cache is never dirty, so a fill never writes back. ares charges 48 (`cpu/cpu.hpp:209`).
- **Write buffer:**
  - It has 4 entries of up to 64 bits each. SB/SH/SW/SD each use 1 entry, and a D-line writeback uses 2.
  - Up to 4 stores cost 1 cycle each (nemu64-test, hardware).
  - Steady-state drain for **uncached 64-bit RDRAM stores is about 18.4 CPU (12.3 RCP) per entry**. That comes from n64brew's hardware memset benchmark: 25.7 ms per MiB with 64-bit uncached writes.
  - A 5th store stalls until a slot frees. NEC says "has a space". The R4300i datasheet says "until the buffer is emptied". **Conflict, not resolved by any measurement.** Throughput is identical either way, and only the burst shape differs.
  - RCP-register and PI writes: no measurement exists. The MiSTer floor is 3 RCP plus 2 SysAD cycles, about 5 RCP ≈ 7.5 CPU **[inference]**.
- **Read-after-write ordering:**
  - Uncached loads, D-fills and I-fills **wait behind every older buffered write**, because the R4300i flush buffer also carries the read ("R/W" bit; "able to take one read memory reference at a time", datasheet p.9).
  - The only exception is a miss's own dirty victim, which goes after its fill.
  - Functionally confirmed by n64-systemtest `spmem: SW`, which does two uncached writes and an immediate read-back that sees the new values.
  - ares writes synchronously, so ordering holds but there is no cost.
- **SysAD ↔ RCP:**
  - MasterClock:PClock is **1:1.5** (NEC Table 1-1 p.35; datasheet DivMode `01 = 1.5:1`; `CONFIG_EC_3_2` in `PR/R4300.h`).
  - SClock = MasterClock (NEC §10.2 p.260). Every SysAD cycle is 1.5 PClock, so there is a 1-2 PClock synchronization cost on entry (NEC Table 11-1).
  - Write data pattern is **D** (one word per SClock). IPL1 writes `EP=0` (`N64-IPL/src/pifrom.s:63`).
  - Per-transaction costs are in the SysAD table below.

## Details

### Why the manual's order wins over MiSTer's

- **NEC says it three ways.**
  - §4.9: dirty data "is stored in this buffer until the requested data is returned from the external interface".
  - §11.3.2: "A new line replaces the missed line, and the data in the write buffer is written to the main memory".
  - §12.5.2/12.5.3: "The above read operation must be completed before the data in the dirty state is written."
- **The R4300i datasheet repeats it** (p.8 cache text and p.9 flush buffer text). It is a separate MIPS document for the same core.
- **MiSTer is the only source with writeback first.**
  - The FIFO gives `datacache_wb_ena` priority (`cpu.vhd:719`).
  - The data cache sequences WRITEBACK1ADDR → WRITEBACK1/2WRITE → WRITEBACKDONE → FILL.
  - This is a simplification that keeps the cache state machine single-line. The test suites cannot see it: nemu64-test only times clean misses, and the memset throughput is order-independent.
- **The order matters for timing.**
  - Manual order: an isolated dirty miss stalls about 40, and code then runs during the writeback.
  - MiSTer order: it stalls about 40 + 27-31 ≈ 67-71.
  - ares: it stalls 80.

### Derivations from the n64brew memset benchmark

The benchmark is on the n64brew MIPS Interface page, under "Repeat Mode", "Memset benchmarks for 1MiB of data":

| Method | Time |
|---|---|
| 64-bit uncached writes | 25.7 ms |
| 64-bit cached writes | 49.8 ms |
| RSP DMA | 2.58 ms |
| MI repeat | 3.80 ms |

- **Uncached:** 25.7e-3 × 93.75e6 / (1 MiB / 8) = **18.38 CPU per SD**. The loop is store-bound once the buffer fills, so this is the per-entry drain period [inference].
- **Cached:**
  - 49.8e-3 × 93.75e6 / (1 MiB / 16) = **71.24 CPU per line**.
  - In steady state every line is a store miss with a dirty victim. A 1 MiB sweep through an 8 KiB D-cache means each line was last written by the same memset.
  - Per line, that is 2 SD issues + loop overhead + fill stall + wait for the previous line's writeback.
  - With the fill at 40 and 2-4 issue cycles, the writeback occupies **≈ 27-31 CPU** [inference].
  - A 4-word block write therefore costs about 9-12 CPU more than a 2-word one (18.4). That fits two 64-bit RI/RDRAM transfers instead of one [inference].
- **Caveats:**
  - The page does not publish the loop code, the VI state, or whether a final writeback flush is included. The flush would be ≤ 512 lines of 65536, under 1 %.
  - The time resolution is 0.1 ms, which is 0.4 % of 25.7 ms.

### Read-after-write: what is and isn't known

- **Known:**
  - Reads are queued in the same flush buffer as writes (datasheet R/W field).
  - Only one read may be pending at a time (NEC §12.6.2).
  - A hardware-validated test reads back its own uncached writes immediately (n64-systemtest `spmem: SW`). The suite's "Weird"-level tests encode hardware-only quirks, for example the `spmem: SH` behavior. The README does not state a pass list.
  - libultra's write-then-read register idioms depend on this ordering.
- **Not known:** how long a load waits behind N pending writes on hardware. The model above is the sum of the remaining drains plus the read latency [inference]. A nemu64-style test would settle it: N×SW uncached to RDRAM or VI_CONTROL, then LW, with N = 0..4.

### What ares does

- **Writes are synchronous and free.**
  - `CPU::busWrite` calls `bus.write` immediately (`cpu/memory.cpp:130-132`).
  - RCP devices charge `DefaultWriteCycles = 0` (`memory/io.hpp:4`, comment "not implemented until we implement the CPU write queue").
  - RDRAM writes charge nothing (`mi/bus.hpp:73-94`).
- **Dirty misses run writeback then fill.** Both are synchronous and cost 40 each (`cpu/dcache.cpp:7,16,54-58,83-87`).
- **The recompiler shares these paths.** Its inline hit path only updates the dirty mask (`cpu/recompiler-ipu.cpp:336-360`). Misses fall back to `DataCache::read/write`.
- **No read is ever delayed by earlier writes.**

## New sharp questions

1. **Isolated dirty-miss stall on hardware.** Is it about 40 (manual order) or about 67-71 (writeback first)? Test: a dirty victim, then a timed LW miss, then a run of ALU work, and time it. Then time a second miss issued immediately after, which should expose the writeback occupancy.
2. **Write-buffer release point.** When the buffer is full, is it "has a space" (NEC) or "emptied" (R4300i datasheet)? Test: 4-8 back-to-back uncached SW to RDRAM, timing each store.
3. **Per-target drain.** What is the drain for SW vs SD to RDRAM, and for SW to an RCP register (VI/SP/MI) or the PI? Test: N stores, then an uncached LW to a different target, with N = 0..4.
4. **Does an RCP-register write's EOK hold depend on the device?** For example, an SP_STATUS write that halts the RSP, or a DP register write.
