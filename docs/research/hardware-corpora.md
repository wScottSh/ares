# Existing hardware capture corpora

Research for #29. Inventory of public, console-captured N64 data that the timing model can be built and checked against, mapped to the calibration requests in #16.

Method: shallow clones at the commits listed below (fetched 2026-10-05), web pages fetched the same day. Clones live outside the repo under `C:\Users\Scott\n64-timing\scratch\r29\clones\`. Values quoted in this doc were read from the cited file. Values marked "derived" are arithmetic on those values. Values marked "inferred" are interpretation. No ROM was run for this doc.

## TL;DR

- One public corpus has RDP counter data from a console. Thar0/RDP-Timing-Tests has 100 fill-rectangle configurations timed with DPC_BUFBUSY and DPC_PIPEBUSY over 1000 runs each. It is the only public check on the RDP span cost, and it agrees with the cen64-jgemu span law to 0.2% (derived).
- CPU-side and PI/SI latencies have self-checking, console-derived expectations in nemu64-test, n64-systembench, and rasky/n64_pi_dma_test.
- No corpus names the console model, board revision, or whether an Expansion Pak was installed. Every corpus is "region NTSC or not stated". The map target (NTSC NUS-001 with Expansion Pak) is never confirmed.
- Of the 15 calibration requests in #16, none is fully answered by public data. 12 are partly answered. 3 have no public data: write-buffer and CACHE-op costs (#5), RDP command buffer depth (#8), and atomic-primitive cost (#19). MM bench scenes, inside the issue body, also have none.
- The jgemu dpc_probe raw tables are still not public (see `research/jgemu-dpc-probe`).

## Derived checks against the Thar0 data

All values below are Thar0 `sample_results.txt` milliseconds x 62,500. Arithmetic is ours.

- The cen64-jgemu span law predicts 14 + 240 x (320 x 129/128 + 12) = 80,294 clk for the 1-cycle, write-only, no-Z, no-VI rectangle. Thar0 measured a 80,462 minimum. The law is 0.2% low.
- With every pixel failing alpha compare (no reads, no writes), 1-cycle is 77,772 = 240 x 324 + 12, and 2-cycle is 155,052 = 240 x 646 + 12. Only one rectangle size was tested, so the per-line vs per-primitive split is inferred.
- Writes add about 11 clk per 320 px line (335.2 vs 324). The law's "+12 per span" therefore appears to be mostly memory, not compute (inferred).
- Z read/write with every pixel failing Z costs 106,118, against 105,942 for Z read-only. Fully rejected spans write almost nothing.
- FB and ZB in the same bank cost 274,646 against 225,518 in separate banks for Z read/write pass. That is about 205 clk per line of row-conflict cost.
- PIPEBUSY stays within 0.2% of BUFBUSY even when memory stalls double the runtime. PIPEBUSY therefore counts stall cycles. DPC_CLOCK was not recorded, so CLOCK minus PIPE cannot be computed from this data.

## Shortlist to wire into the verification harness first

Ranked by how much timing-model behavior each one checks per unit of wiring effort. Every item runs a ROM in the emulator, so none needs its data committed to ares. That matters for the corpora with no license.

1. **Thar0 RDP-Timing-Tests.** It is the only public RDP counter data from a console, with 100 configurations covering span compute, memory writes, IM_RD, Z, VI priority, and bank conflicts. The alpha all-fail configs are exact (min = avg = max), so they make a zero-tolerance test. Wiring work: build the ROM with libdragon, route debugf output to the harness, and compare against `compare.py` `hw_data`. MIT.
2. **nemu64-test timing group.** CPU cache miss, uncached load (with VI contention), write buffer, and COUNT:DP_CLOCK ratio, self-checking. Its failures in ares are already catalogued in `research/nemu64-timing-failures`. MIT.
3. **n64-systembench.** One ROM grades CPU, RCP register, PI, and SI latencies. No license, so run it from outside the repo.
4. **rasky n64_pi_dma_test.** 24,512 PI DMA timing points (64 alignments x 383 lengths) with register and data checks. It is the densest DMA dataset. No license, so run it from outside the repo or keep a local copy.
5. **snapper64 and repeater64.** They check pixels, not cycles, but they catch timing-model changes that reorder RDP state updates (no-sync leaks, fill-color latching, span buffer behavior). MIT.
6. **Thar0 RDP-Noise.** Replay the console arrays against the noise generator. It is small, but the noise phase depends on how many cycles the RDP steps, so a timing change that moves the LFSR shows up here.

The PeterLemon timing ROMs, n64-systemtest, hcs64, the n64brew wiki, and TASVideos are reference text or weak composite checks. They do not earn a harness slot ahead of the six above.
