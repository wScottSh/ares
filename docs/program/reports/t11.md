## Deviations

1. **No devices/events.\*.** The events live in timing/events.hpp and timeline.cpp, and ViFetch is VI::Fetch in vi/. T8 placed SpDma in rsp/dma.cpp the same way.
2. **Files the plan did not name:**
   - ri/bus.cpp (VI_DMA device tag), rdram.hpp (friend drop), system/serialization.cpp (v153.9-vifetch);
   - behaviors.tsv, behaviors.py (unit vclk/px) and the spec;
   - n64-run (ri_vi, vi_tear and the VI::fieldScanned host hook), mmbench.py (files vi_ lines), the bench report.py and the rdram-private.cpp comment.
3. **The report.py hpos fix.** The hpos window opens at the line change the sync loop saw, so that line's refresh stalls the sync poll and never a sample. The old outliers_per_line therefore read 0.667 under any model. It now counts per HSYNC inside the sampled span.
4. **Burst count.** A 128 B segment that crosses a 2 KiB row splits in two, so a line has 3 x ceil(width x bpp / 128) bursts plus the row crossings.
5. **New row vi.vclk-per-pixel 4** (wiki, vi-fetch.md: H_SYNC 3093 is a 773.5-px line). It converts H_VIDEO pixels to VCLKs.
6. **No reference, so the model chose:**
   - Registers are read per line, with no field latch.
   - A line still fetching at the next HSYNC keeps fetching, and the new line fetches nothing.
   - A sample outside the 3 fetched lines reads 0.
   - The AA mode is not consulted: 3 lines in every mode. MM runs mode 0 and nemu64's vi_init runs mode 2.
   - Fetch and compose rows follow ares's 480-row display window.
7. **Sketch items not built.** There is no hidden-bit line buffer, because compose does not use coverage. There is no underrun counter, because compose runs at the last grant.

## Follow-ups

- **The VI's contention is too strong for the hardware data.** The VI takes 8.9% of the channel, inside the research band. Its cost to other clients is still about 5x what five hardware measurements allow:

  | Measurement | Model | Hardware |
  |---|---|---|
  | nemu64 other-bank uncached mean | 37.9 | 32.5 (VI off 32.54) |
  | Uncached memset | 19.70 pclk/SD | 18.38 |
  | Cached memset | 75.77 pclk/line | 71.24 |
  | RSP DMA memset | 6.08 B/rclk | 6.5 |
  | SP DMA 4 KiB write | 5.85 B/rclk | 6.5 |

  The same-bank row-miss part matches: the median rises by 4, as on hardware. The excess is CPU and DMA waits behind 24-rclk VI bursts.
  - Unmeasured inputs: vi.burst (model-choice), ri.overhead-read (an SP DMA fit, applied to VI by ADR assumption) and ri.rank.vi. It is also unknown whether the n64brew memset table was measured with the VI on; the vi-off model points sit within 1-2% of it.
  - A what-if refit of sysad.rdram-write-period and sysad.rdram-block-write-period to 11 rclk and ri.overhead-write to 0 gave 18.16, 74.19 and 6.425. None reaches its band on the rclk grid, so it was reverted and the fits are unchanged. Their notes and the vi.burst note record the numbers.
  - Deciding experiment: the bench's vi-on and vi-off memset points on hardware (calibration #16).
- C7 Load Miss VI-off x8 are the other remaining nemu64 timing failures (T7a follow-up).
- Debug-only "VI DMA reading ... modified in the cache" notices on MM rose from 106 to 257 (128 B burst reads).
