## 2. pi-io-write phase walk
Reproduced on head (pi-io-write.z64): sb_rclk 133, pass (132..136). Raw: min=94 ticks (125.33 rclk), max=140, sum=5052 over 50 reps. (5052-94-140)/48 = 100.375 ticks = 133.83 rclk. Worker said max 160 and mean 133.86; I read max 140 and 133.83. Conclusion unchanged, but those two numbers in the report are not what the shipped ROM prints.
Base runner on the head ROM also reads 133, so the pass is the ROM change, not the core. Base runner on base ROM: 140 (fail).

Sawtooth, measured: I patched a scratch copy of the kernel to a fixed N nops (N=0..49) after the write and ran it on the head runner (results/verify-76/fix.txt, phase-scan-patch.diff).
- pi-io-write: 140,140,140,140,140,141,141,142,142 (N=0..8), then 125 at N=9, rising to 141 at N=33, then 125 again at N=34 (period 25 nops ; 25 pclk = 16.7 rclk). Range 125..142, mean of the 50 integer readings 133.46. N=0 sits at 140: the old single-phase fail was one tooth point.
- si-io-write: range 2149..2166, same 25-nop period, mean 2157.5.

Judging the worker's argument. The phase-lock claim is credible but inferred: VI off, interrupts off (main.c:623-624), loop and stack cached, one master clock. I would add that the PClock/SClock ratio (3:2) can only give a rep-to-rep phase difference of at most 3 pclk, tiny against the 25 pclk poll period, so hardware reps are effectively one phase (inferred; I could not test hardware). Therefore hardware 134 is one unknown point on its own sawtooth, which is about 8 rclk wide on each side.
Is averaging over phase fair? No, it is not a like-for-like comparison. It computes the model's expectation over a uniform phase and compares it with a single draw. The mean passing at 133.8 vs 134 says the model busy time is within about 8 rclk of the hardware reading, not within 2. It manufactures a pass (and the old 140 manufactured a fail) in the same way. What the evidence does support: the hardware reading 134 lies inside the model's phase range 125.3..141.3 (measured here as 125..142).
Label the check should carry: not `check` with band 132..136. Either (a) `check` with band = the model's phase range [125.3, 141.3] and the stated reason "hardware reading is one phase of a 16.7 rclk poll sawtooth", or (b) report-only. I prefer (a) with the label "consistent-with". The same applies to si-io-write (band 2153.7..2162.3, true phase uncertainty about +-8.3), si-dma write64 (+-8.1 is accidentally about right) and write64-rom (+-4.3). The three new "measured" values (pi.io-busy 134, si.io-busy 2158, si.write64-rom 2144) each carry about +-8 rclk of hardware poll quantization that the rows do not say. The expected.tsv pi-io-write note does disclose the caveat (inferred), so nothing is hidden; the label just overstates the precision.
Also: do not refit PiIoBusy (agrees with verify-75). TIMEIT_MULTI drops the min (a legitimate 125.3 tooth point) and the cold max, so the retained set is slightly asymmetric; effect about 0.2 rclk, negligible.

Boot-phase experiment (item 5 key finding). Method: scratch copy of romgen with a counted delay loop at the ROM entry (`N64_BOOT_DELAY=K`, 4 instructions + 3 pclk per iteration, code size constant), bench ROMs rebuilt per K, run on the base runner and the head runner (same ROMs), 49 values of K each (1..14, 100..200 step 4, 1..400 step 3, Fibonacci to 1597). Patch: results/verify-76/phase-scan-patch.diff; table: dense.txt.
- sp-dma-sweep wr-4096-off0 b_per_rclk (band 6.49..6.515): base core 6.169 (31x), 6.321, 6.334 (5x), 6.495 (11x), 6.678. Head core 6.169 (18x), 6.321 (4x), 6.334 (14x), 6.495 (12x), 6.678. Spread 6.169..6.678, 8.2%, around a 6.5 target. In band at about 22-24% of boot offsets, on both cores. The worker's 6.169..6.508 over four layouts is confirmed and the range is larger.
- mi-memset-rspdma b_per_rclk: base core 6.492..6.500 over 49 offsets, all 49 in band. Head core 6.422..6.501: K=1..9 gives 6.422/6.436 (fail, 9 of 49), K>=10 gives 6.496..6.501 (pass). The shipped ROM boots at the 6.42 plateau on head (6.423). So mi-memset-rspdma's pass->fail in this PR is real on this ROM, but the head model has a boot-phase-dependent plateau (step at about 30 pclk of boot delay) that the base model did not show in 49 samples. A one-line boot delay flips it back to pass. I did not trace the mechanism. Hypothesis, untested: thread scheduling against an absolute-time event such as legacy.pif.step-quantum (40960 pclk).
- pi-dma-sizes cart-to-ram-8 alternates 196.0 / 197.33 (one COUNT tick) with K on both cores; band 191.07..194.93 fails at both values.
- pi-io-write (walked) reads 133 at all 16 K tested on head: the walk removes boot-phase dependence.
Plain statement. sp-dma-sweep's verdict follows boot phase: on master it fails at 6.169 and would pass at about one boot offset in four. That check's past fails (and the one pass-at-6.495 seen when bench ROM bytes moved in commits 1-2) are phase noise, not model signal. I only tested master and head cores; I did not check earlier commits, so "since T8" is untested, but nothing in the master core changed that makes T8-era behavior different in kind (inferred). mi-memset-rspdma was stable on master (49/49 pass), so its earlier pass was real on that core; its head fail is a plateau, also boot-phase dependent.
Recommendation: the bench harness should walk boot phase (run each rate-style ROM at several entry delays and assert on the median or report the range). That is a structural fix (a one-time harness change), not more notes.
