# Build sequence

Each unit is one branch in the linear stack (preferences.md line 12), started from the previous unit's head, delivered as a PR targeting that branch. Each unit ends green on its own check; the check is a run of the built emulator through the harness (`C:\Users\Scott\n64-timing\build\harness`, `n64-run`), never a compile. "Baseline" means the per-frame TSV (`frame, fb_hash, cpu_cycles, rsp_busy_clocks`, plus the new bus counters once they exist) produced by the previous unit on the same ROM and frame range. Test ROMs: nemu64-test `9a8b9f7` (`timing`, `cycle`, `cop0hazard`), n64-systemtest `196f542`, and sweep ROMs this plan adds under `tools/timing-roms/` (built with libdragon, not committed as binaries). MM bench: 600 frames, 4 scenes, the fork's `emux` readout.

Order rationale. Units 1 to 3 change no cost and prove the scaffold is bit-for-bit neutral (foundational-thinking, scaffold first). Unit 4 is the first behavior and the first time a hardware number is asserted. CPU units come before the RDP because nemu64 gives exact pass/fail per row and because the RDP's bus stalls are meaningless until the CPU and VI masters exist. The RDP is split into three units so that the content port (11) is checked by console dumps before any timing is attached (12). Unit 14 is last because the budget is a property of the whole.

What to measure first, before writing code, is unit 0's host seconds per scene for the interpreter. The design's cost estimate (rationale.md) assumes ~30 ns per emulated CPU instruction after the scoreboard; unit 1 and unit 6a each re-record host time so the per-unit cost of the scaffold and of the scoreboard is known separately.
