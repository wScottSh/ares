# Plan: everything before the console run (PREHW_COMPLETE)

This plan covers the work the program can still do before console hardware becomes unavoidable. It replaces `green-plan.md` as the active plan. The green plan reached SOFTWARE_COMPLETE on master `1e7c9bdd5` (after #142). Its sections 1, 3 and 8 still bind every unit here. Master is now `82aa2e7b6` (after #144, U-143). #144 changed only SOFTWARE_READY clause 1's re-time test and `wall-budget.tsv`; the results tsv, its counts and the closure draft's clause verdicts below are the same on both commits (measured, `behaviors.py --check` and the closure draft on the merged branch). Line numbers in `behaviors.py` below are for `82aa2e7b6`.

Six read-only investigations produced the evidence on master `1e7c9bdd5`. They covered the bus and CPU, PI and SI, the RDP, MM, the behavior rows and the kit, and tooling and docs. The planner reproduced four of their findings before this plan relied on them. Those four are the pidma row-crossing split, the merge of mm-decomp-60fps#1, the MI repeat path, and the kit's PIF terminate call. Each claim carries a label: measured (read from a run or the live state), cited (file and line, URL, or commit), inferred, or guess.

## 1. PREHW_COMPLETE

### Definition

Let N be the set of open items. Each has an id:

- every check in `docs/spec/n64-timing-results.tsv` whose result is not `pass`: fail, consistent-only, pass-conditional, and every pending result except `pending:calibration-16` on a `hw:*` check. The id is the check id. A check that a unit adds and that does not pass (U-NEMU-2022 can add failing checks) joins N the same way;
- every SOFTWARE_READY and MAP_GREEN clause that the closure draft reports as not holding. The ids are `clause:sr-1` to `clause:sr-6` and `clause:mg-1` to `clause:mg-5`, numbered in the closure draft's table order. `clause:sr-1` is the re-timed wall budget. `clause:mg-1` is SOFTWARE_READY, `mg-2` file select, `mg-3` mm-decomp-60fps#1, `mg-4` hw ingestion and `mg-5` the verified rows;
- every behavior row that is not verified (MAP_GREEN clause 5). The id is the row id. An excluded row (an `undecidable.tsv` entry starting `not-hardware-decidable`) stays in N as a class D row, so clause 4 has rows to check and an exclusion is recorded, not dropped; a D row never blocks.

`tools/n64-timing/calibration/blockers.tsv` holds one row per id with the columns `id`, `kind`, `class`, `seed`, `decider`, `unit`, `separates`, `signed` and `searched`.

The seed is not stored. It is the commit that first adds `tools/n64-timing/calibration/blockers-seed.tsv` (`id`, `class`), computed as the oldest result of `git log --first-parent --diff-filter=A --format=%H -- tools/n64-timing/calibration/blockers-seed.tsv` on the run's commit. U-PREHW-PRED-2 adds that file once. The seed is not the commit that first adds `blockers.tsv`, because U-PREHW-PRED adds `blockers.tsv` first (a56b13743 on feat/u-prehw-pred), with classes from this plan's earlier text (the JOY and read64 reports as C, vclk-pal as A) and other clause ids. A row's seed class is its class in `git show <seed>:tools/n64-timing/calibration/blockers-seed.tsv`. The `seed` column of `blockers.tsv` is a copy, and PRED fails if it differs from the seed commit's class. PRED also fails if `blockers-seed.tsv` at the run's commit differs from the seed commit's. No line in either file names the seed, so editing a file cannot move it. An id that joins N after the seed (a check U-NEMU-2022 adds, a clause that starts failing) has no seed class; its `seed` cell is `-`, and it counts as seed class B: it reaches C only through a unit whose Scope names it (clause 3), and it can never be D (clause 4).

PREHW_COMPLETE holds when all of the following hold. `behaviors.py` computes clauses 1 to 6 from the repository: U-PREHW-PRED (PR #148) computes clause 1, clause 2, the decider part of clause 3, clause 4 against a frozen id list, and the standing-run part of clause 6; U-PREHW-PRED-2 makes clauses 3 to 6 mechanical as written here. Section 4 states what each of the two lands. Clause 4 and the `seed` checks read git history; with no git, they print "not computed" and PREHW_COMPLETE does not hold.

1. **Every open item has exactly one blocker row.** A row whose id is green or not in N is an error.
2. **No row is class A or B.** No software-doable work is left (section 2 defines the classes).
3. **Every class C row names a console measurement that separates the fork from an alternative.** `clause:mg-4` is exempt from this clause; clause 5 gives its decider.
   - Its `decider` is a `questions.tsv` id, `comparable(kit, q)` holds (`behaviors.py:1122`), and the id appears in that question's `closes` column, or the check's `hw:*` twin does.
   - For a fit row, the question does not re-run its fit (`reruns_fit`, `behaviors.py:1128`).
   - `separates` has the form `at=<question> <key> <metric>;fork=<value>;alt=<value>;cite=<reference>` or `at=<question> <key> <metric>;fork=<value>;mut=<value>;cite=<unit>`. `at` names one of the row's deciders and one value it compares (a question compares many points and metrics, so the fork value is a value only once one is named); `<key>` and `<metric>` are as `kit.py` names them. PRED evaluates the question's own rule with the fork value as the model side and each of `fork`, `alt` or `mut` as the console side. The rule must accept `fork` and reject the other. For an `ext:` question PRED uses that question's own comparator (for example Thar0's 1%).
   - `fork` is read from the standing run, not typed. PRED takes the model side of the question from the run the closure draft names (the same values `kit.py` compares, lo..hi over boot delays and pads), and fails if the `fork=` cell differs from it. `behaviors.py --results` writes those values to `docs/spec/n64-timing-fork.tsv` beside the results, under the same `# standing run` header, so `--check` reads them without the run directory.
   - `alt` is a value from a cited published source or law. The unit verifier opens the cited source, confirms the value, and names its report in `signed`. PRED fails on an `alt` with an empty `signed`. An `alt` more than 4 tolerances from `fork` must also be a number printed in the source, and its `cite` must point at it (`path:line` or a URL with `#L<n>`). An `alt` derived from a source by arithmetic, such as a cited value moved by one poll period, must lie within 4 tolerances. The bound is 4 because the rule rejects anything past 1 tolerance, and two models give separable console readings only when their accept bands do not overlap, past 2. Four is twice that minimum: an `alt` inside it shows the question resolves a shift of a few tolerances, and a value such as 10× the fork, which any rule rejects, does not pass. For an `exact` rule the tolerance is 0 and the bound does not apply; `alt` must lie outside the fork's value set.
   - `mut` is the value a scratch model mutation gives, where the mutation is fixed in this plan's unit row before the unit measures. Its `cite` names that unit, and it must lie within 4 tolerances of `fork` (past that, the question cannot resolve it: U-SEPARATES outcome (b)). A fit row needs an `alt` when one is published, and the `alt` source must not be the fit's own data. When U-SEPARATES' alt search finds none, the fit row takes U-SEPARATES' resolution mutation like any other row (D9). Its `mut` is then enough only if `cite` is `U-SEPARATES` and `searched` lists the alt search's sources, each with its result.
   - A row whose seed class is A or B names in `unit` a unit of section 4 whose Scope cell contains the row's id (PRED reads the section 4 tables, splitting cells on unescaped `|`, and matches the id as a whole word). That stops a row reaching C by relabeling alone or by naming an unrelated unit. It applies whatever the row's class now is. A row seeded A or B that is relabeled C on a comparable question that already closes it still needs a `separates` value the question's rule rejects, a `fork` equal to the run's and, for an `alt`, a `signed` report; free text or an accepted value fails this clause (self-tests in U-PREHW-PRED-2).
   - `searched` lists the published sources and hardware recordings checked, each with its result. It is not computed; the unit verifier re-checks it.
   - An out-of-kit row instead names an `undecidable.tsv` id that starts `not decidable by this kit` and whose text has a `What would decide it` sentence. These stay open for decision D1. A row whose seed class is A or B (or that has no seed class), or whose `unit` is U-SEPARATES, may go out-of-kit only when its entry also cites an instrument-resolution limit showing that no kit point can resolve the row, and the unit verifier names its report in `signed`; PRED fails such a row with an empty `signed`, whichever unit it now names. A unit that took the row over (U-SEPARATES outcome (b), U-LABELS-2's flash and cart rows) therefore cannot move it out of the kit unsigned. A question that cannot resolve the row's mutation is not that reason (section 4, U-SEPARATES outcome (b)): accepting it would let PREHW_COMPLETE hold by moving rows out of the kit.
4. **Every class D row was D at the seed and is excluded.** Its seed class is D, and its `decider` is an `undecidable.tsv` id whose reason starts `not-hardware-decidable` and is unchanged since the seed commit (`git show <seed>:...`). A row cannot become D after the seed. Today's six D rows are listed in section 2.6.
5. **Every clause row has a decider PRED can check.** `clause:sr-2` to `sr-6`, `mg-1`, `mg-2` and `mg-5` are aggregates: class `follows`, decider `follows`, and PRED checks that every id the clause lists as failing has its own row. `clause:mg-3` is class A until U-MAP-D3 computes it. `clause:mg-4` (every `hw:*` check ingested and passing) is class C with decider `hw-run`, the explicit decider for ingestion. This is an exemption from clause 3: no single `questions.tsv` question decides ingestion, so `clause:mg-4` has no `questions.tsv` decider and no `separates`, and PRED applies this check in their place: PRED requires that every `hw:*` check's question is comparable and that the dry run of clause 6 moved every `hw:*` check to pass. `clause:sr-1` is class A whenever it fails (re-time the scenes); it is never C.
6. **SOFTWARE_COMPLETE clauses 2 to 4 hold, and the standing run is current.** The standing run names current master. `det` and `stepcap` pass. `dry-run.sh` moves every `hw:*` check (89 today, more as units add questions) from pending to pass, which proves wiring only (green-plan section 8). `behaviors.py --results` runs it on the standing run's `calib/` and records each `hw:*` check's result in `docs/spec/n64-timing-dry-run.tsv` under the run's header; clause 5's `clause:mg-4` check reads the same file.
7. **Every unit in section 4 has landed or is closed with a stated reason** (`units.tsv`, not computed). Every open issue and pull request on wScottSh/ares other than #1, #16 and this plan's own units is closed or named in a C row's `searched` or decider. On `82aa2e7b6` that means #77, #100 and PR #139 (U-PREHW-CLOSE).

Three parts of this cannot be checked by a machine. Clause 7 depends on the coordinator's ledger. The `searched` cell is honest only if the unit verifier re-checks it. The `alt` value and its `cite` are honest only if the verifier who names its report in `signed` opened the source; PRED checks only that `signed` is filled and that a far `alt` points at a line. Every unit that writes a `searched` or `separates` cell gets those checks from its verifier. The rest is computed, so a self-declared class alone cannot satisfy the predicate.

### Classes

| Class | Meaning | Ends when |
|---|---|---|
| A | Software-doable now, using a cited published reference or an existing hardware recording: a fix, a correct label, or a correct check | the unit lands; the item turns green or becomes C |
| B | Software-doable tooling (kit point, ROM, reader, question, comparator) that lets the console run decide the item | the unit lands; the item becomes C |
| C | Only console data decides it; the kit question exists, is emitted by a kit ROM, and has a reader | the console run (#16) |
| D | No console can decide it | never; excluded |

"A, then C" means an unexplored recording exists. The unit compares the model with it and records the result. If the item is still not green after that, the kit question is what remains. No A unit may fit a value to the recording it compares against (green-plan section 8, prefs 7, 21 and 31).

## 3. MM file select (#11): one mechanism for both screens

The plan's file-select rule is unchanged: each row is judged on its median over the mmbench phase sweep (green-plan section 3).

**What the model does now.** The following comes from the research agent's run of `framelog.py` on `results/plan-rdp/filesel/base4` (measured).
- In the named screen, 1-field and 2-field frames do the same RDP work: busy 15.48 vs 15.44 ms, with identical triangle, load, setter and sync counts. They differ in the gfx start offset after retrace (0.28 vs 0.47 ms) and in RSP audio overlap (1.60 vs 1.85 ms). The correlation of frame time with that offset is 0.80.
- So the model's named cadence is set by scheduling jitter at a margin of about 0.2 ms.
- Named does 0.53 ms more RDP busy than empty (15.45 vs 14.92 ms). Frame time spreads 0.87 ms (p10 to p90) in both screens.

**What only named draws.** Each file name draws 8 glyphs twice (shadow, then main). Each glyph is a `gDPLoadTextureBlock_4b` 16x16 I4 plus a `gSP1Quadrangle` with combiner TEXEL0×PRIM (mm-decomp `z_file_choose_NES.c:1393-1408`, cited). For 2 files that is 32 textured quads, 64 triangles and 32 loads. The measured delta is +70 triangles and +35 loads, with about 6 px per added span (measured).

**Why every tried mechanism failed.** A uniform cost moves both screens. A per-triangle constant has no window: +150 rclk fails empty at 1.0515 while named reads 1.8774; +200 gives 1.0847 and 1.9607 (measured, `plan-rdp/filesel/tri*.log`). U-RDP-DRAIN (#139) swaps which screen passes (empty 1.1513 fail, named 1.9383 pass; verify-139). The three u-93 arbitration readings move only the details (verify-137).

**The one mechanism that could pass both.** The named-only work is short textured triangle spans of about 6 px. A cost that applies to short textured spans, and not to the empty screen's work, is the one candidate selective enough. The model has no reference for spans under 16 px. cen64 confirms its span law's width independence only "for w>=16" (`rdp_core.c:5354-5355` @2f8d7bc, cited). The other path is less scheduling jitter (RSP audio and yield timing). That path changes the spread, not the work.

**What reference could ground it.** No published source gives short-span or textured-triangle cost. The research searched these:
- Thar0 (fill rects only);
- n64brew RDP and Pipeline (sync waits only, already modeled);
- cen64 (rects, w>=16);
- MiSTer, whose RTL is itself too fast on this screen (N64_MiSTer#27, "OoT and Majora's Mask Initial Menus Run Too Fast", open);
- the SDK autofill demo (no numbers);
- pro-man ch. 12 (no numbers);
- web searches for console cadence captures (none beyond captures U and W).

parallel-rdp, angrylion and libdragon were not checked. They are not timing sources, but that is inferred.

So the grounding must be a console measurement of the named-only work in isolation. The existing questions cannot provide it. `triangle-setup` (`questions.tsv:73`) builds only untextured 1 px types and does not close mm:filesel-named. The `mm-filesel` rule passes any console value inside the fork's per-frame range, which is about 1.8 ms wide on named, so a 0.3 ms shift still passes (u-mmr-filesel, inferred).

**Units.** U-GLYPH adds the isolated measurement. U-FS-DETAIL makes the BENCH comparison report the gap and the spread. After the console run, any model change is fit to the glyph kit data, and mm:filesel-named becomes its independent check. No unit tunes a constant toward 2.00 (green-plan section 8).

## 7. What not to do

Green-plan section 8 binds unchanged. In addition:

- Do not fit the pidma row-crossing points or the PR #2 rows. They are comparison data, and any later model value fit to the kit's console data must keep pidma and PR #2 as independent checks.
- Do not add a per-triangle, per-load or per-span constant for file select. The measured triangle series has no window, and any value would be a file-select fit.
- Do not change `pi.block-writeback` for row-crossing DMAs before the kit's console data exists.
- Do not choose between the EEPROM 6 ms and 15 ms references, or between the PIF 5 s and 6 s references, without console data.
- Do not count the 87-check dry run as anything beyond wiring.
